Refresh Opportunity Scoring: A Decision-Support Ranking for Content Review Prioritization

Which pages should a content reviewer look at first — and how much better is a learned ranking than a hand-written rule, honestly measured?

§Abstract

This study asks which content pages a search team should review first, given limited reviewer capacity, using FlyRank's anonymized starter content dataset (30,000 pages, 32 clients). A hand-written baseline rule — combining staleness, visibility, and current decline status — was built first and audited against real signal checks before any modeling began. A random forest classifier, trained on eight observable, pre-decision signals and validated with a client-grouped split to prevent memorization, was then compared against that baseline using a fairness-matched precision metric. The model's top-ranked candidates matched the baseline's guaranteed-correct set with 96.2% precision without ever seeing the label directly, while a deliberate leakage test confirmed the evaluation harness itself was sound (ROC-AUC jumped from 0.580 to 1.000 when a label-derived feature was intentionally added, then removed). The result is offered as decision-support for content review prioritization, not as a causal or production-ready system.

1.Introduction & Problem Statement

The decision this work supports, who acts on it, and why a plain rule falls short.

Content teams have far more pages than review time. The practical question isn't "which pages are bad" — it's "which pages should a reviewer look at first this week," given that a typical review cycle can realistically cover on the order of dozens of pages, not thousands.

This work supports that prioritization decision directly. The intended user is a content strategist or SEO editor working down a ranked list, deciding whether to refresh, expand, protect, or simply monitor each page. The cost of a wrong call is asymmetric: flagging a healthy page wastes a modest amount of reviewer time, while missing a genuinely declining page lets the problem compound, unnoticed, for longer.

A hand-written rule can only check a small, fixed number of conditions ANDed together. Early testing of a rule this shape ("stale AND visible") found it matched only 35 of 22,006 visible pages (0.2%) — far too narrow to be a usable queue on its own. This motivated testing whether a learned ranking, built from the same observable signals, could produce a more useful prioritization without sacrificing the transparency a reviewer needs to trust the list.

2.Data

Which release, which fields, what was deliberately excluded, and why.

This study uses FlyRank's anonymized starter content dataset: 30,000 rows, one row per pseudonymized content page, across 32 pseudonymized clients, with all activity metrics aggregated over a trailing 90-day window. Identifiers (content_id, client_id) are pseudonyms used only for grouping and splitting — never as model features.

What was deliberately excluded

  • FlyRank product-decision flags (e.g. a composite health score, priority score, or action-type flag) were not shipped in this dataset at all, and would not have been used as model inputs even if present — using a product's own decision as a training feature just teaches a model to reproduce that decision, not to find independent signal.
  • trend_direction and trend_pct were excluded from every model's feature set. The target label is computed directly from trend_direction, so including it (or its numeric sibling) would hand the model the answer.
  • Rows with no position data (avg_position = 0, meaning "not measured," not "rank zero") were excluded from position-based aggregates to avoid corrupting the signal.
A named limitation of this slice: client history depth is an unbalanced panel — some clients have much more tracked history than others — and this 30,000-row starter slice is a teaching cut, not the full ~79M-row warehouse. Results here describe this slice; they are not claimed to generalize to the full warehouse without re-validation.

3.Methodology

Task framing, label definition, baseline, features, and validation design.

Task type

This is a ranking / scoring problem, not classification or clustering: the question is "which pages first," so the natural evaluation is Precision@K — of the top K pages a method ranks first, how many are actually correct by the label.

Target / proxy label

The label used throughout is is_declining = (trend_direction == "down") — a within-current-window proxy, not a true observed future outcome. This is stated explicitly rather than treated as a forward prediction: the model ranks "currently pattern-matches declining pages," not "will decline next month." A stronger future-window label (prior 90 days of features predicting an actual outcome over the next 30 days) was identified as the natural next step but was out of scope for this slice, which does not carry the daily time-series needed to construct it.

Baseline

A transparent, hand-written baseline rule was built and audited before any modeling:

baseline_score = stale × visible × declining × impressions_90d
where stale = (days_since_last_update ≥ 180), visible = (impressions_90d ≥ 100), declining = (trend_direction == "down")

Two signals behind this rule were checked directly against the data before being trusted:

SignalVerdictEvidence
Staleness → decline rateMIXEDDecline rate rose from 0.583 (0–30 days stale) to 0.743 (181+ days), but the strongest bucket had only n=35 — too small to trust alone.
Position → CTRCONFIRMEDMean CTR rose monotonically from 0.055 (deep, n=879) to 0.355 (page 1, n=8,633) — a clean, well-supported signal.

Features

Eight observable, pre-decision signals were used: impressions_90d, days_since_last_update, avg_position, ctr, content_age_days, word_count, sessions_90d, engagement_rate. Every feature is knowable at the moment of ranking — none is derived from the label or from a future window.

Model

A random forest classifier (200 trees, max depth 6, class-weight balanced) was trained alongside a fully readable depth-3 decision tree for comparison, following the principle that added complexity should only be kept when it earns a real improvement over a simpler, explainable model.

Validation design

A client-grouped split (GroupShuffleSplit on client_id, 80/20, seed=42) was used rather than a random row split. Pages from the same client can share hidden structure (site template, writing style, niche) that a random split would let a model memorize rather than genuinely learn from — the honest question is whether the ranking holds up on a client the model has never seen.

A methodology problem was found and corrected during this work: the baseline rule flags only 26 pages total out of 30,000. On the client-holdout test split, zero of those 26 landed in the 7 test-set clients — meaning a naive Precision@50 comparison on that split measured tie-break order among identically-zero-scored rows, not real rule performance. This was caught by explicitly counting non-zero baseline scores in the test set before trusting the metric, and corrected by matching K to the baseline's real candidate count (K=26) rather than an arbitrary K=50.

The random forest's top-26 ranked pages matched the baseline's guaranteed-correct set with 96.2% precision — without trend_direction or trend_pct ever appearing as a feature. This indicates the model located substantial real signal in the eight observable features alone, rather than needing the label handed to it.

Caveat on this number: the K=26 comparison above was computed on the full dataset (train and test combined) for the tree and random forest, not the held-out client-split test set, so it is partly in-sample and likely somewhat optimistic versus true generalization to unseen clients.

Leakage audit

A full leakage audit was run against the final feature set, following an 8-point checklist (timeline, label-derived columns, product flags, population selection, split design, base rate, feature-importance sanity check, and a deliberate add-back test).

The add-back test confirmed the evaluation harness works correctly: deliberately adding trend_pct (the literal numeric source of the label) as a feature pushed ROC-AUC from 0.580 to 1.000 — a clean demonstration of what leakage looks like when it occurs. This column was never present in any of the actual reported model results; the test exists to prove the harness would have caught it if it had been.

Error examples

Inspecting the model's false positives revealed a consistent pattern: three of the clearest wrong cases all shared days_since_last_update = 104 and near-zero CTR (0.0–0.1) despite meaningful impressions (209–4,037) and reasonable positions (5.5–20.0). This suggests the model leans on volume and position even when CTR is anomalously low — a case where a page may simply never have earned a strong click-through rate, rather than being in genuine decline.

5.Limitations & Honest Framing

What this work can say, and what it explicitly cannot.

Observed On this 30,000-row starter slice, a random forest trained on eight observable signals ranked candidates that matched a hand-written baseline's guaranteed-correct set with 96.2% precision at a fairness-matched K.

Directional Position and impressions carry real, measurable signal for this decline proxy in this dataset; staleness alone is a weaker, noisier signal that should not be trusted in isolation.

Decision-support The ranked queue is intended to help a human reviewer decide where to spend limited time first — it is not a guarantee that any specific page will decline, and it does not claim that refreshing a flagged page will cause recovery.

  • The label is a same-window proxy (trend_direction == "down"), not a validated future outcome — this is not a forecasting model.
  • This is an observational, cross-sectional comparison. No experiment was run, so no causal claim is made or supported.
  • Results describe a 30,000-row, 32-client starter slice. They have not been validated against the full warehouse release or on clients outside this sample.
  • No claim is made about Google's ranking algorithm. Nothing here models or infers how search engines rank pages — only patterns observed within this portfolio's own performance data.

6.Ranked Recommendations — Action Playbook

Turning the ranked score into a practical, human-reviewed queue.

The model's decline score was mapped to four actions, calibrated to match realistic reviewer capacity rather than flagging most of the dataset as "urgent":

An earlier, looser threshold (0.65/0.50) was tested first and rejected: it flagged 14,584 pages — roughly 65% of the dataset — as needing review, which defeats the purpose of a prioritized list. Thresholds were tightened specifically so the "urgent" tier reflects a realistic multi-week reviewer workload rather than relabeling most of the portfolio as important.

Human review requirements — before acting on any flag

  1. Confirm the decline isn't seasonal, a sibling page absorbing traffic (consolidation), or a tracking anomaly. One inspected top-ranked page showed an excellent position (4.9) paired with an unusually high CTR (4.93%) — verified as real data, not an error, but exactly the kind of case that needs a human look before assuming the flag is straightforwardly correct.
  2. Check whether the page was recently edited outside the tracked update field — a stale timestamp can reflect a data lag, not true staleness.
  3. Confirm the page still matters to the business; a low-priority flag is not evidence a page is worthless, only that it didn't match the observed pattern.

What should never be automated

  • Auto-publishing content changes based on the score alone.
  • Auto-pruning or deleting no_action pages — absence of a flag is not evidence of worthlessness.
  • Applying this model to a client outside the training sample without a human first confirming the same signals transfer.
  • Presenting the score to a client as a performance guarantee — it is an internal prioritization aid only.

Monitoring & retrain triggers

  • Manual audit precision on the top tier drops meaningfully below the ~0.73–0.96 range observed here.
  • New clients differ substantially in industry or content style from the 32 in the training sample.
  • The label definition changes (e.g. a move to a true future-window label, as recommended above).
  • At minimum quarterly re-validation, since search behavior and site content both drift over time.
